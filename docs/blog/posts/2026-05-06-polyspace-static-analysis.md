# 代码静态分析实战：用 Polyspace 揪出隐藏 Bug

动态测试（Tessy）保证功能正确，静态分析（Polyspace）保证代码本身没问题。两者互补，都是 ISO 26262 要求的验证手段。

## 静态分析和动态测试的区别

| | 静态分析 | 动态测试 |
|------|----------|----------|
| 运行代码 | 不需要 | 需要 |
| 发现什么 | 运行时错误、安全漏洞、编码规范 | 功能逻辑正确性 |
| 覆盖率 | 理论上可覆盖所有路径 | 依赖测试用例设计 |
| 典型工具 | Polyspace | Tessy |

## Polyspace 两大引擎

**Bug Finder**：用语义分析扫描代码，找出潜在缺陷。类似于编译器开最高警告，但比编译器聪明得多——编译器只能检查语法，Bug Finder 能发现除零、空指针、数组越界等运行时问题。

**Code Prover**：用抽象解释法**证明**代码不存在特定类型的运行时错误。不是"可能有问题"，而是"绝对有"或"绝对没有"。

> Code Prover 的分析精度远高于 Bug Finder，但耗时也长得多。通常开发阶段用 Bug Finder 快速扫一轮，提测前用 Code Prover 深度分析。

## 使用工作流

```
创建工程 → 导入源码和头文件 → 配参数 → Run → 看结果 → 逐条处理
```

### 几个关键参数配置

**1. 必须勾选「Ignore default initialization of global variables」**

C 标准默认未初始化的全局变量会赋 0，但这个"隐性初始化"可能掩盖代码逻辑错误。勾选后 Polyspace 会报未初始化变量，强制你显式写 `int x = 0;`。

**2. 「Verify module」模式**

非完整程序（没有 `main()`）选这个。Polyspace 会自动生成一个 `main()` 函数，初始化指定变量、调用指定初始化函数、按任意顺序调用指定函数。

**3. MISRA C 检查**

在 Coding Standards 里勾选需要检查的规则集。我们项目主要用 MISRA C 2012 + MISRA AC AGC（自动生成代码规则）。

## 结果解读

分析完代码会标四种颜色：

| 颜色 | 含义 | 处理优先级 |
|------|------|-----------|
| 绿色 | 可证明安全 | 无需处理 |
| 红色 | 确定有运行时错误 | **立即修复** |
| 橙色 | 可能存在运行时错误 | 需要审查确认 |
| 灰色 | 不可达代码 | 确认是废弃代码还是逻辑错误 |

**橙色是最容易被忽略的**——它不是确定有问题，而是"证明不了没问题"。需要人工判断：是真的有边界风险，还是被调函数的约束条件没传进来（stubbing 不够）。

## 常见坑

- **大量橙色**：大概率是 Stubbing 没做好。全局变量和函数参数没加数据约束，Polyspace 会假设所有值都可能出现
- **编译错误**：缺头文件路径或宏定义。在 Include 和 Macros 里补上
- **分析时间太长**：降低 Precision 等级或提高超时时间
