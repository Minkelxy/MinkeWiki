# 嵌入式单元测试实战：Tessy 从入门到覆盖率

单元测试这词对嵌入式工程师来说不陌生，但真正在日常开发中同步写测试用例的人不多——至少我以前不是。直到项目要求满足 ISO 26262 ASIL 等级，才被迫认真学了一遍。

## 为什么单元测试值得做

两个最有说服力的理由：

**1. 规避低级错误**

再高明的工程师也会犯错。最基本的条件判断、数据移位出错——这种问题如果拖到集成测试才暴露，定位成本翻十倍。单元测试在编码阶段就能捕获。

**2. 代码改动验证**

旧代码的测试用例对重构后有意义的。正常版本升级时大部分功能没变，跑一遍旧用例，结果能佐证新代码没影响老功能——这就是回归测试的核心价值。

## 测试框架都干什么

不管用 Unity、CppUTest 还是 Tessy，框架提供四件事：

| 功能 | 说明 |
|------|------|
| 用例编写执行 | 定义输入输出，自动运行比对 |
| 断言方法 | EQUAL、TRUE、FALSE 系列宏 |
| 覆盖率检测 | 语句/分支/MC/DC |
| 报告生成 | 测试结果 + 覆盖率报告 |

## Tessy 工作流

Tessy 是商业工具，比开源框架多了图形界面和团队协作。完整流程：

```
创建工程 → 添加源文件 → 分析代码 → 打桩 → 设置输入输出 → 创建用例 → 执行 → 看覆盖率 → 补用例
```

### 分析代码阶段常见报错

- **宏定义报错**：源码编译环境的宏要在 Tessy 里重新定义（`_HIGHTEC`、`TASKING_` 等）
- **缺失头文件**：换编译环境后可能引入不存在的头文件，屏蔽即可
- **汇编语句**：用汇编的地方尽量屏蔽，Tessy 不认

### 打桩的三种方式

被测函数调用的其他函数需要"打桩"（stub）隔离：

| 方式 | 适用场景 |
|------|----------|
| 普通桩 | 无返回值的简单函数 |
| 高级桩 | 需要返回值的函数，可设预期值 |
| 手写桩 | 需要传参检测、局部数据处理 |

### 覆盖率

ISO 26262 按 ASIL 等级要求不同覆盖率：

- ASIL A/B：语句覆盖 + 分支覆盖
- ASIL C/D：再加 MC/DC

一个关键认知：**不应该先覆盖再用例**。应该按需求分析 → 等价类 → 边界值设计用例，设完后看覆盖率暴露的代码问题（废弃代码、不可达代码），再补用例。否则容易陷入"1+1=3 的代码，测试证明了 3=1+1"的自证陷阱。

## 团队协作技巧

Tessy 支持以函数为单位导入导出（tmb 或 Tessy Script 格式）。复杂函数由开发者本人写用例（理解最深），简单函数交给测试同事，最后合并。

## 一些实用技巧

- 遇到 Tessy 因循环卡死：临时 `#undef` + `#define` 降低循环次数
- 寄存器读写：用 `#define` 把寄存器改为函数，函数再打桩给出变化的输入输出
- 圈复杂度预检：用开源工具 Lizard，命令行 `lizard -C 15 ./src` 即可
