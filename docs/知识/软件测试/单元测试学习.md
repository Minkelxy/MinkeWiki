## 单元测试介绍

### 常见的测试流程

常见的单元测试流程通常包含以下几个步骤：

1. **测试计划与设计**：

   - **需求分析**：理解待测试代码的功能需求、性能指标、边界条件等。
   - **测试用例设计**：基于需求，编写详细的测试用例，包括输入数据、预期输出、边界条件、异常场景等。确保测试用例覆盖关键路径、边界条件、错误处理路径以及正常工作流。
   - **确定测试策略**：选择自顶向下、自底向上、基于风险等测试方法，规划单元测试与其他测试阶段（如集成测试、系统测试）的关系。

2. **编写测试代码**：

   - **创建测试环境**：搭建必要的测试框架，如 Google Test、CppUTest 等，配置编译选项和测试运行脚本。
   - **编写测试函数**：为每个测试用例编写独立的测试函数，函数内调用被测代码并使用断言（如`assert()`或框架提供的断言函数）验证实际结果与预期结果的一致性。
   - **实现模拟对象**（可选）：如果被测代码依赖外部资源，编写模拟对象（stubs 或 mocks）以替换真实依赖，确保测试的隔离性。

3. **执行测试**：

   - **编译测试代码**：确保测试代码能够成功编译，没有语法或链接错误。
   - **运行测试**：执行测试框架提供的命令或脚本运行所有测试用例。
   - **收集结果**：测试框架自动捕获测试结果，包括通过/失败信息、测试耗时、可能的错误堆栈跟踪等。

4. **结果分析与缺陷定位**：

   - **评估测试覆盖率**：使用代码覆盖率工具（如 gcov、lcov 等）分析测试用例对源代码的覆盖程度，确保关键路径和边界条件都得到了充分测试。
   - **分析失败原因**：对于失败的测试用例，查阅测试报告、日志或错误堆栈，定位问题所在。可能需要重新审视测试用例设计、检查被测代码逻辑或排查依赖问题。
   - **回归测试**：修复缺陷后，重新运行受影响的测试用例，确保问题已解决且未引入新的故障。

5. **测试报告与文档**：

   - **生成测试报告**：整理测试结果，生成详细的测试报告，包括总体通过率、失败测试的详细信息、覆盖率统计等。
   - **更新相关文档**：根据测试结果更新设计文档、用户手册等项目文档，反映实际实现与预期功能的相符程度，记录测试过程中发现的需求澄清或变更。

6. **持续测试与维护**：
   - **代码重构与新增功能测试**：随着代码的重构或新功能的添加，及时更新测试用例，确保测试集的完备性和有效性。
   - **定期回归测试**：在软件开发周期的不同阶段（如版本迭代、性能优化后）进行回归测试，验证现有功能的稳定性。
   - **监控测试覆盖率趋势**：长期跟踪代码覆盖率，确保随着项目的演进，测试覆盖度不会下降。

### 测试指标

单元测试的测试指标主要用于衡量测试的有效性和完整性，以下是几个关键的测试指标：

1. **代码覆盖率**：

   - **语句覆盖率**：测量测试用例执行了多少源代码中的可执行语句（如 C 语言中的语句或表达式）。通常要求达到一定比例（如 80%）以确保大部分代码路径得到测试。
   - **分支覆盖率**（或条件覆盖率）：衡量测试用例是否覆盖了程序中每个控制流分支（如 if-else 语句）的取真和取假分支。同样，可能设定一个阈值来确保分支逻辑得到充分验证。
   - **MC/DC 覆盖率**（Modified Condition/Decision Coverage）：对于安全性或可靠性要求极高的系统，可能要求达到更严格的覆盖率标准，MC/DC 确保每个决策条件独立影响决策结果，适用于复杂的逻辑判断。

2. **测试用例执行结果**：

   - **通过率**：计算通过的测试用例占总测试用例的比例，高通过率通常表明代码基本功能的正确性。
   - **失败率**：记录失败测试用例的数量及其原因，用于定位问题并指导代码修复。
   - **阻塞/未执行**：记录因依赖问题、环境问题等导致无法执行的测试用例。

3. **圈复杂度**:

- **圈复杂度**：衡量程序或模块的复杂度，通过计算程序控制流的分支数量来评估程序的测试难度和潜在的错误风险。
- **计算方法**：通过遍历程序中的每个控制流分支，计算每个分支的入度（入度表示该分支被其他分支依赖的次数），然后求和得到圈复杂度。
- **阈值**：根据项目需求，设定一个阈值，如 10、20 等，用于评估圈复杂度是否过高，过高的圈复杂度可能会导致测试难度增加，影响测试效率和覆盖度。

### C 语言如何编写利于单元测试的代码

网上关于如何编写利于测试的代码的例子大都使用面向对象的语言作为实例,虽然 C 语言没有面向对象,但写驱动的时候也经常会写出类似结构的代码,出现的问题也值得推敲.

#### 清晰目的

因为我最初上手是测别人写的代码,对不了解细节的人,单元测试最难的部分还是搞清正确的输入输出关系.即使代码有充分的说明,对于一些分支和数学运算或者具体业务有关的代码,要求一个旁观的人能知道什么样的输出是正确的还是有些强人所难了.
所以单元测试一般还是会给代码的编写者去做,毕竟作者最懂自己的目的.但如果一定要旁人测试,我思考我自己测试中遇到的问题,其实在一个模块里需要仔细斟酌测试输出的地方并不多,这些函数的特征也都比较明显,如果配以一些说明,不管是对结果的简单描述,还是对可能的测试用例的描述,都可以帮助测试者更好的理解代码.
退而求其次,也希望函数是包含了注释的,再其次至少也要函数名称能展现他的用途.

#### 全局变量

tessy 提供了很多便利工具,使得一些问题被隐藏.其中最明显的就是全局变量的滥用.tessy 很方便的可以使全局变量作为输入输出,测试的时候不会很麻烦,但也带来一些隐含的问题,一些数组被定义为全局变量,多个模块使用这一数组,而这些数组实际上是常量,这似乎不应该出现,测试时也很不方便,在不通读代码的情况下,你很难确认这样一个数组到底是常量还是变量,输入还是输出.这种情况使用参数形式传入数组或者指针对编写用例的人来说会友好很多,代码结构也更好了,减少这类不必要的全局变量.

## 编写利于测试的 C 语言代码

### 1. **清晰目的与文档化**

#### a. **明确注释与函数说明**

- **函数注释**：每个函数应附有详细的注释，说明其功能、输入参数、返回值、行为边界条件（正常情况、异常情况等）、可能触发的错误码（如有）。这有助于测试人员快速理解函数意图，设计合适的测试用例。

  示例：

  ```c
  /**
   * 计算两个整数的和。
   *
   * @param a 第一个加数
   * @param b 第二个加数
   * @return 两数之和。如果输入值超出了int类型的最大值，返回INT_MAX。
   */
  int add(int a, int b);
  ```

- **模块或文件注释**：对于包含多个相关函数的源文件，提供总体描述，概述其主要功能、内部数据结构、依赖关系及外部接口等。

- **内联文档**：在代码关键位置（如复杂算法、条件判断、循环等）添加内联注释，解释其逻辑和目的，便于测试人员定位和理解潜在的测试点。

#### b. **测试用例描述或示例**

- **编写测试用例指南**：为重要或复杂的函数编写一份测试用例指南，列举预期的典型输入、预期输出、边界条件以及可能触发的异常情况。这可以作为测试人员编写测试脚本的参考。

- **代码示例**：在函数文档中提供简短的代码片段，演示如何正确调用该函数以及处理返回值。这有助于直观展示函数的使用方式和预期行为。

### 2. **避免或合理使用全局变量**

#### a. **减少全局变量的使用**

- **参数化**：将原本作为全局变量使用的常量数据或状态信息作为函数参数传递，明确数据依赖关系，使测试更易于模拟各种输入条件。

- **封装与隐藏**：对于确实需要全局共享的数据，使用静态全局变量或`extern`关键字声明的外部变量，同时将其置于单独的头文件中，并通过函数接口访问。这样既能控制全局变量的可见性，也能降低耦合度，便于测试。

#### b. **明确全局变量性质**

- **常量声明**：使用`const`关键字声明真正的常量全局变量，表明其不可变性，方便测试人员识别并避免尝试修改。

- **命名规范**：全局变量应遵循一致且具有描述性的命名规则，如前缀`g_`、全大写等，以区别于局部变量，同时在注释中注明其用途和更新策略。

### 3. **管理寄存器操作**

#### a. **封装硬件交互**

- **硬件抽象层（HAL）**：对于直接涉及寄存器操作的底层代码，设计硬件抽象层接口，将具体的寄存器访问、配置操作封装在内。测试时，可以 mock 或 stub 这些接口，以便隔离硬件影响，专注于软件逻辑测试。

#### b. **文档化硬件交互**

- **硬件手册引用**：在涉及寄存器操作的函数或模块注释中，引用相关的硬件手册或数据表页码，方便测试人员查阅硬件特性和操作规则。

- **寄存器操作注释**：对于关键的寄存器读写操作，添加注释描述操作的目的、影响的硬件状态以及与上下文的关系，帮助测试人员理解其在系统中的角色。

### 4. **代码结构与设计原则**

#### a. **模块化与高内聚低耦合**

- **函数单一职责**：确保每个函数只负责一项具体任务，避免函数过于庞大和复杂，使得测试能够聚焦于单个功能点。

- **分层设计**：按照功能或责任划分代码层次，如应用层、业务逻辑层、驱动层等。测试时，可以逐层进行，先验证底层驱动的正确性，再逐步向上测试高层逻辑。

#### b. **接口设计**

- **错误处理**：设计统一的错误返回机制（如返回码、异常抛出等），确保函数在遇到错误时能够明确告知调用者。测试时，需覆盖各类错误场景。

- **边界条件测试**：特别关注函数处理边界条件的能力，如空指针检查、溢出预防、空数组处理等。在函数文档中明确指出这些边界条件及其预期处理方式。

### 5. **测试支持**

#### a. **提供测试框架或辅助函数**

- **测试宏**：定义用于辅助测试的宏，如断言宏、打印调试信息宏等，简化测试代码编写。

- **测试模式开关**：在代码中引入测试模式标志，允许在测试时启用额外的日志记录、数据校验等功能，而在生产环境中关闭，不影响性能。

#### b. **持续集成与自动化测试**

- **编写测试脚本**：为项目配备单元测试、集成测试等自动化测试脚本，并纳入持续集成流程，确保每次代码提交都能及时得到测试反馈。

- **代码覆盖率分析**：利用工具（如 gcov、lcov 等）进行代码覆盖率分析，确保测试用例覆盖到关键路径和分支逻辑，提高测试完整性。

通过遵循上述建议，可以显著提升 C 语言代码的可测试性，使测试工作更加高效、准确，同时也促进了代码的可读性、可维护性和健壮性。
