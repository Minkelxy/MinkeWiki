# MISRA C 实践指南

落地[编程规范学习路线](学习路线.md)的**第 2 步（MISRA C 深入）**。MISRA C 是嵌入式/汽车领域最重要的 C 编码标准——你的 **AUTOSAR / 电机控制**代码方向，合规往往是硬要求（安全件常强制）。本文不讲 100 条规则，讲：**为什么重要、规则怎么分、哪些规则最值钱、怎么用工具落地**。

> 一句话：MISRA C 不是"洁癖"，是把**未定义行为（UB）和易错模式**提前挡在编译器之外的规则集。

---

## 一、为什么 MISRA C 重要（汽车/嵌入式）

| 场景 | 为什么强制 MISRA |
|------|----------------|
| ISO 26262 功能安全 | 安全件开发流程要求"合规的编码标准" |
| 编译器差异 | 嵌入式编译器多，行为不完全一致，规则统一"安全子集" |
| 硬件相关性 | 位操作/内存/volatile 多，普通 C 规范管不到这些坑 |

> MISRA C 由 [MISRA 联盟](https://www.misra.org.uk/)发布，当前主流是 **MISRA C:2012**（含 AMD1-AMD3 增补）。

## 二、规则结构（先懂分类，再记规则）

- **Directive（指令）**：面向过程/设计（如 Dir 4.1：最小化运行期失效）
- **Rule（规则）**：面向具体代码，分三级：
  | 级别 | 含义 | 合规要求 |
  |------|------|---------|
  | **Mandatory（强制）** | 违反=不安全 | 必须遵守，无例外 |
  | **Required（必要）** | 大多数情况要遵守 | 可记录偏差（Deviation） |
  | **Advisory（建议）** | 建议遵守 | 可不遵守但要说明 |

> 落地策略：**Mandatory 必须清零，Required 清零或记偏差，Advisory 按团队选**——别追求全绿，那不现实。

## 三、最值钱的规则主题（高频违规，重点看）

| 主题 | 规则要义 | 典型违规 |
|------|---------|---------|
| **未定义行为** | 禁止 UB（如整型溢出、越界、悬垂指针） | `int` 溢出、数组越界未查 |
| **未初始化读取** | 自动存储对象必须先赋值再读 | 声明未初始化就用 |
| **动态内存限制** | 限制 `realloc` 等不可预测行为 | 嵌入式乱用堆分配 |
| **类型显式转换** | 隐式转换要显式化（essential type 模型） | `float` 隐式转 `int`、窄化无 cast |
| **副作用最小化** | 一个表达式别塞多个副作用 | `if (a && b++)` 这类 |
| **控制流约束** | switch 每个分支要终止、限制 goto | case 里没有 break/return |
| **递归限制** | 有界递归（或无递归） | 无界递归爆栈 |
| **标准库受限** | 禁用危险库函数（abort/exit/realloc 等） | 用了被禁函数 |

> 一句话记忆：**UB 清零、读前先赋值、转换要显式、副作用要少、库要受限**——这五条覆盖了大部分违规。

## 四、怎么落地（工具 > 人工）

| 工具 | 说明 | 适用 |
|------|------|------|
| **[cppcheck](https://github.com/cppcheck-opensource/cppcheck)** | 开源静态分析，内置 MISRA addon（`--addon=misra`） | 免费首选，个人项目够用 |
| PC-lint / Coverity | 商业静态分析，MISRA 支持完善 | 团队/量产 |
| Polyspace | 形式化验证，从严证明 | 安全件（见[软件测试学习路线](../软件测试/学习路线.md)） |

**落地三步**：
1. **跑基线**：对现有代码跑一次 MISRA 检查，统计 Mandatory/Required/Advisory 各自数量
2. **清零 Mandatory**：逐条修或记录偏差（Deviation，注明理由和风险）
3. **设质量门**：新代码合入前跑检查，Mandatory 违规 = 不通过（接 CI）

> 注意：工具报的 MISRA 违规也可能有误报——**先人工确认再修**，别盲改。

## 五、和你现有代码的结合

- 拿[负载率监测软件](../../制作/负载率监测软件.md)、电机控制代码、或 RTOS 相关 C 代码练手
- 对照[编程规范记录](编程规范记录.md)的既有规则（文件头/命名/类型），MISRA 是"安全语义层"，两者互补
- AUTOSAR 项目：MCAL/诊断栈代码直接按 MISRA 标准写，省得后期返工

## 六、本轮项目推荐：跑一遍「MISRA 合规基线」

**推荐做什么**：挑一个你现有的 C 项目（负载率监测软件或电机代码），用 [cppcheck](https://github.com/cppcheck-opensource/cppcheck) 的 MISRA addon 跑一遍，把 **Mandatory 违规清零**（Required 记偏差），产出一份「合规基线」：违规清单 + 修了什么 + 留下的偏差理由。

**为什么值得做**：
- 这是[学习路线](学习路线.md)第 2 步的**落地验收**——不跑一遍，MISRA 就只是"看过"；
- 你的 AUTOSAR/电机方向迟早要合规，**现在就把现有代码做干净**，比安全件项目里临时补容易得多；
- 产出可直接复用：以后新代码按这个基线审，形成你自己的"合规惯例"。

**具体怎么做**：
1. `cppcheck --addon=misra --enable=warning,style <你的代码>` 跑一遍，导出报告
2. 按第三节主题逐条看 Mandatory 违规，能修就修、不能修记 Deviation（理由+风险）
3. 把"修了什么/留了什么"写成一页基线文档，放编程规范子域

**产出**：一份「MISRA 合规基线」文档（违规清单 + 修复 + 偏差记录）→ 进[编程规范记录](编程规范记录.md)配套，也是你 AUTOSAR/电机代码的合规起点。
